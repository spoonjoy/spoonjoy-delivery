# Planning: Spoonjoy Cross-Client Delivery

**Status**: approved
**Created**: 2026-07-20 19:58

## Goal

Build and pilot a small, production-grade delivery system that carries one Spoonjoy product contract through web/backend, native Apple, and MCP/agent implementations to independently verified exact releases and terminal cleanup. Only a provider-backed Release Set may declare a Product Change shipped.

## Upstream Work Items

- Codex task `019f2e25-2fc3-75b2-8ba3-335f3777115a`: its protected source-owner handoff and byte-identical receiver acknowledgment are prerequisites for Unit 13b; it retains exclusive native/TestFlight/provider-release ownership until terminal two-sided validation succeeds.

## Scope

### In Scope

- Establish spoonjoy-delivery as the protected, tested control plane for cross-client contracts, authorization, evidence, finalization, and cleanup.
- Define strict versioned records and semantic validation for Product Contracts, Product Changes, Contract Packs, provider operations, handoffs, attestations, recovery, cleanup, and Release Sets.
- Establish a single-operator V1 authority model with separate least-privilege review and ledger principals, independently verifiable actor/workflow provenance, and append-only ownership/release records.
- Preserve repository ownership boundaries: domain contracts in spoonjoy-v2, delivery coordination in spoonjoy-delivery, and native locks/provenance in spoonjoy-apple.
- Integrate exact-source web/backend, native Apple, MCP/protocol, and agent-experience evidence without moving provider credentials into the delivery repository or untrusted workflows.
- Require compatibility proof for the current and previous native contract/build where the Product Change affects installed clients or queued work.
- Pilot the system on Recipe Photo Studio after the active release task transfers ownership, including semantic parity, live provider evidence, installed proof where hardware exists, and run-owned cleanup.
- Produce durable operator documentation, rollback/containment paths, hostile reviews, and exact release evidence.

### Out of Scope

- A generalized orchestration platform, always-on dashboard, monorepo conversion, generated universal SDK, or broad feature-flag framework.
- Contracting every existing Spoonjoy behavior before the pilot; V1 covers the changed capability and the reusable delivery boundaries it needs.
- Treating screenshots, source-only checks, direct JSON-RPC, copied task status, or deployment-authored summaries as sufficient shipment proof.
- Committing, logging, or artifacting credentials, raw provider responses, personal data, private paths, or unredacted device/account evidence.
- Any mutation or credential-bearing access by this delivery task to source repositories, production Cloudflare, App Store Connect, TestFlight, notifications, source worktrees, or source-owned brokers before the retained release owner completes the protected handoff. The sole delivery-task exception is Unit 13a3's bounded read-only GitHub verification of the retained-owner-supplied exact web/native containing commits, protected-main files, checks, and protection state; it performs no checkout, rerun, review, merge, write, or mutation endpoint. The retained source owner may perform only the root-authorized `source-guardian-cutover-v1`, the disjoint `source-protection-observer-v1` limited to its exact four-read/zero-write App installations, source-owned non-exportable-key read broker, and closed no-redirect Unit 13a3 GET adapter, and the protected-main receiver-ack merges required by the handoff contract under its own still-exclusive authority. Those narrow handoff inputs do not authorize this task and exclude product, deploy, provider-release, TestFlight, notification, cleanup, and unrelated source mutations.
- Folding Apple callback cutover into the Photo Studio Product Change.
- Deleting pre-existing, dirty, ambiguous, or separately owned data, branches, artifacts, builds, or worktrees.
- Claiming cross-repository GitHub concurrency, deterministic hosted-model behavior, or cryptographic immutability against repository administrators.

## Notes

The delivery repository is a control plane and evidence compiler, not another Spoonjoy implementation. It coordinates exact source-owned work and validates provider-backed results while domain behavior remains in the product repositories.

Release evidence must come from independent authoritative queries. Existing deploy and TestFlight summaries are locators, not self-attestation. Native provenance therefore separates the manifest embedded in the signed app from the external attestation that binds that manifest to archive, IPA, build, and provider identity.

Product Changes remain mutable coordination records. Only an effective Release Set with exact publication observation and cleanup is shipment authority; later corrections append new records instead of rewriting prior evidence.

Evidence classification and exact-manifest cleanup are product requirements. Public artifacts contain allowlisted sanitized facts and digests; private evidence expires after verification; forbidden data never enters repository history.

The canonical implementation algorithms, schemas, state machines, timing boundaries, provider routes, crash matrices, TDD units, and verification commands live only in the adjacent doing document.
